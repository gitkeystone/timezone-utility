# timezone-utility 项目章程（Constitution）

## Core Principles

### 一、代码质量优先（Code Quality First）

代码质量是所有变更的不可协商前提。任何提交必须满足：

- 提交前必须通过静态检查（linter/formatter）与类型检查；不得携带未经说明的抑制项或未处理警告。
- 命名必须自描述；函数与模块必须保持单一职责；重复代码必须在合并前消除或显式抽象。
- 每个公开 API 必须提供文档；非显而易见的实现必须注释"为什么"，而非复述"是什么"。
- 死代码、未使用依赖与调试残留必须在合并前移除。
- 复杂度（圈复杂度、嵌套深度、函数长度）超过约定阈值时必须拆解并书面说明理由。

Rationale: 可读、简单、无重复的代码是可维护性与可测试性的基础，质量不能靠事后返工补救。

### 二、测试标准（Testing Standards）

测试是行为正确性的唯一可信来源，遵循测试优先（TDD）纪律：

- 新行为必须遵循"先写测试 → 确认失败 → 实现 → 通过"的 Red-Green-Refactor 循环。
- 关键路径与用户可见行为必须同时具备单元测试与集成测试。
- 合并门槛：全部测试必须通过；不得以 `skip`/`xit`/注释绕过失败测试，除非附 Issue 编号并限期修复。
- 测试必须确定性（无 flaky）；测试不得依赖真实网络或系统时钟，时间与时区相关逻辑必须注入可控制的时钟。
- 覆盖率必须达到约定阈值，且覆盖率下降不得进入主干。

Rationale: 测试既是回归防护，也是安全重构的信心来源；不确定的测试等同于没有测试。

### 三、用户体验一致性（User Experience Consistency）

面向用户的界面与行为必须一致、可预测、向后兼容：

- CLI 输出、错误信息与返回结构必须遵循全局统一格式；任何用户可见变更必须遵守向后兼容规则。
- 错误提示必须措辞一致且可操作；错误码/退出码语义必须全局统一。
- 命名、参数顺序、默认值等用户可见约定必须集中定义并复用，禁止各模块自行发明变体。
- 用户可见行为的每次变更必须写入变更日志，并按语义化版本规则升级版本。

Rationale: 一致、可预测的体验降低用户认知负担并建立信任，是产品可用性的组成部分。

### 四、性能要求（Performance Requirements）

性能以数据驱动，且是功能正确性的一部分：

- 性能必须量化：在功能设计阶段即明确延迟、内存、启动时间等预算，而非事后补救。
- 禁止主观的"感觉慢"判断；任何性能结论必须基于基准（benchmark）或剖析（profile）并保留基线数据。
- 必须关注渐进复杂度；禁止引入明显低效算法或 N+1 类反模式。
- 优化必须由测量驱动（先 profile 再优化）；不得以牺牲可读性与可测试性换取未经验证的微优化。
- 性能回归必须纳入持续集成或基准测试，回归不得静默进入主干。

Rationale: 性能问题一经进入生产即代价高昂，必须在设计期用可测量的预算加以约束。

## 技术决策机制（Technical Decision Framework）

- 影响架构、依赖选择或公开契约的技术决策，必须记录为 ADR（Architecture Decision Record），包含：背景、备选方案、取舍、结论与后果。
- 决策必须可追溯：相关 PR/提交必须链接到对应决策记录或 Issue。
- 默认采用最简方案（YAGNI）：在满足当前需求的前提下，选择复杂度最低、依赖最少的方案；引入额外复杂度必须显式论证收益。
- 引入新依赖前必须评估：维护活跃度、许可证、体积/构建影响、与现有技术栈的一致性；禁止引入功能重复的依赖。
- 每项决策必须逐一对照本宪章四大原则（质量/测试/用户体验/性能）检查其影响。
- 影响面大或有争议的决策必须在合并前取得评审共识，并保留分歧记录。

## 实施方案选择（Implementation Approach Selection）

- 存在多个可行实现时，必须显式列出候选方案，并依据统一评分标准（质量、可测试性、用户体验一致性、性能、维护成本）比较后选定。
- 被否决的方案及其否决理由必须记录，避免重复评估。
- 优先复用团队既有模式、现有抽象与官方推荐做法；偏离标准做法必须说明理由。
- 对高风险或不确定的方案，必须先以最小可验证原型（spike）验证可行性，再投入正式实现。
- 涉及破坏性变更的实施必须附带迁移/兼容计划（如弃用期、迁移脚本、版本升级说明）。
- 实施顺序必须按依赖与风险排序：先消除不确定性与高风险项，再实现低风险增量。

## Governance

- 本宪章是项目治理的最高准则，约束力高于其他实践指南、编码习惯或临时约定；冲突时以本宪章为准。
- 原则的增删、重新定义，或与宪章冲突的例外，必须通过正式修订流程，并记录修订理由与影响范围。
- 版本遵循语义化版本：MAJOR（原则移除/重新定义）、MINOR（新增原则或实质性扩展）、PATCH（措辞澄清与修正）。
- 合规评审：每次合并前必须对照本宪章核查四大原则与决策/实施机制的符合性；任何违反必须有明确授权与记录。
- 修订须同步更新版本行并保留历史，便于追溯。
